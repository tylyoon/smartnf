# 레시피 분류·예상 맛·사용자 취향 v1

## 화면과 데이터

나라·문화권: 한식, 중식, 일식, 이탈리아식, 프랑스식, 동남아식, 인도식, 멕시코식, 미국식, 기타, 퓨전, 미분류.
역할: 메인, 사이드, 겸용, 기타, 미분류. 겸용 음식은 메인/사이드 필터 양쪽에서 검색된다. 재료 태그를 별도로 만들지 않는다.

기존 MyRecipe 원본 JSON을 변경하지 않고 V22 `my_recipe_taste`에 회원+레시피 번호로 추가 저장한다. 기존 레시피는 기본 이름 규칙으로 분류를 제안하고, 사용자가 레시피별 AI 분석을 요청해 검토·저장한다. 모든 레시피를 저장 순간에 자동으로 LLM 호출하는 구조는 아니다.

예상 맛은 매운맛, 단맛, 짠맛, 신맛, 감칠맛, 기름진 정도 6축이다. 0은 거의 없음, 5는 매우 강함. 식감·향은 짧은 설명이다. 모델이 식품을 맛보거나 측정한 값이 아니며 양념·제품·조리에 따라 달라진다. 빈 값은 자료 없음이며 0으로 취급하지 않는다. 모델 실패 시 맛 숫자를 만들지 않는다. 사용자 수정은 USER 출처로 저장된다.

사진은 식단 카드에서 4:3 비율로 통일하고 출처를 이미지 바깥에 둔다. 모바일은 1열, 중간 폭은 2열, 넓은 화면은 3열이다. 사진 없는 카드도 공간을 유지한다. MyRecipe 음식명·분류를 강조한다. 사진 수집처/승인/검색 제외 로직은 이번에 수정하지 않는다.

## 실제 평가와 취향 계산

- 실제 먹은 뒤 입맛 평가(좋아요/보통/아쉬워요), 다시 먹고 싶은지, 실제 맛 강도, 너무 매움/달음/짬/심/기름짐을 선택한다.
- 현재 평가 한 건을 레시피별로 저장한다. 다시 저장하면 이전 평가를 수정한다. 평가를 미입력으로 저장하면 해당 평가를 지운다. 날짜별 식사 기록은 만들지 않는다.
- 동일한 음식명은 여러 번 저장해도 취향 통계에서 한 음식으로 세며, 최근 저장된 레시피 중 평가가 있는 첫 항목을 사용한다.
- 각 맛 축에 유효한 서로 다른 음식 3개 이상이 있어야 평균을 계산한다. 좋아요+다시 먹기 거부가 아닌 음식은 실제 강도를 사용한다. 너무 강하다고 표시한 축은 실제 강도에서 1단계 낮춘 값을 사용한다(최저 0). 이 1단계 보정은 초기 서비스 규칙이며 검증된 감각 모델이 아니다.
- 저장된 예상 맛과 이 평균의 차이를 기준으로 취향순을 제공한다. 비교에 필요한 축이 없는 레시피는 뒤에 둔다. 기존 아쉬워요/다시 먹기 거부는 정렬에서 불리하게 반영한다.
- 소수점 취향 평균은 선호 추정값이지 맛 적합 확률이 아니다. 모델 가중치를 재학습하거나 자동 파인튜닝하지 않는다. 평가 데이터로 애플리케이션의 선호 기준을 갱신한다.
- 맛 정렬은 영양·질환 적합성이나 알레르기 안전성 판정이 아니다. 기존 헬스케어 기능과 별도이며, 이 단계의 취향 정렬에 개인 건강 조건을 자동 적용하지 않는다.

## 자연어 검색

로컬 LLM은 검색문을 나라, 역할, 포함/제외 단어, 최대 조리시간으로 해석한다. 실제 결과는 자신의 MyRecipe 이름과 저장 재료 목록에서 결정한다. 검색 조건을 한국어로 보여준다. 새로운 레시피를 검색 결과로 만들어 넣지 않는다.

현재 재료 검색은 정규화한 문자열 포함 검사이다. 모든 식재료 동의어·세부 부위를 확장하는 검색은 아니다. 예를 들어 돼지고기와 삼겹살의 관계를 별도 사전으로 완전히 보장하지 않으므로 제외 재료 검색을 알레르기 검증으로 사용해서는 안 된다. 모델 연결 실패 시 전체 입력 문구를 그대로 검색하고 그 상태를 표시한다.

## API·보안

- GET /api/me/recipes/taste: 내 저장 레시피, 분류/평가, 취향 평균.
- POST /api/me/recipes/taste/{number}/analyze: 소유 레시피만 로컬 모델로 분석, 자동 저장 없음.
- POST /api/me/recipes/taste/{number}: 검토한 분류·예상 맛·실제 평가 저장.
- POST /api/me/recipes/taste/search: 내 레시피 자연어 검색.

기존 회원 인증·CSRF를 유지하고 모든 SQL에 회원 ID를 포함한다. 현재 화면 계정 표식을 요청에 넣어 오래된 탭의 다른 계정 쓰기를 막는다. 저장 revision 불일치는 409로 거부한다. 부모 레시피 행 잠금 및 트랜잭션으로 저장을 직렬화하고, 원본 삭제 시 FK CASCADE로 평가도 삭제한다. 응답 no-store. 원문/평가/모델 응답을 로그에 출력하지 않는다. 모델 요청은 기존 localhost:8091 별칭 smartnf-food-parser를 사용한다.

## 검증한 범위

- Java 21 및 실제 Spring 7.0.1/Jackson 3.0.2 API로 변경 Java를 컴파일했다. 회원 식별 의존성은 검사에서만 대체했으며 기존 실제 CurrentHealthMember를 프로젝트에서 변경하지 않았다.
- 실제 JdbcTemplate + H2 MySQL 모드: V22 생성, JSON 저장/재조회, 회원별 분리, 소유하지 않은 번호 거부, revision 충돌, 취향 평균, 문자열 검색, 삭제 CASCADE 검사 통과.
- 실제 Java HTTP/JSON 어댑터를 로컬 응답 fixture로 검사: 정상 분류, 범위 밖 맛 강도 거부 및 기본값 복귀, 검색 조건 해석 검사 통과. 실제 Qwen 모델 추론 품질 검사는 아니다.
- 실제 JS를 JSDOM에서 실행: 분류 필터, 예상 맛 막대, 평가 저장, CSRF/계정 헤더, 검색 조건 표시 검사 통과. 변경 JS 문법 검사 통과.
- 이 환경에서 Gradle 배포 서버 접속 실패로 전체 Spring Boot 빌드/기존 테스트는 실행하지 못했다. Chromium은 실행 환경의 소켓 제한으로 열리지 않아 실제 브라우저 스크린샷·모바일 시각 검증은 하지 못했다.
- 사용자 Windows의 MySQL V22 적용, 실제 모델 응답, 실제 화면·재로그인 복원은 확인이 필요하다.
