# SmartNF 공통 등록 연결 기준

현재 구현 범위는 식품 선택 초안과 명시적 확정 등록의 분리 및 공통 목록 UI다. 실제 MyPage 템플릿/Controller/회원 API가 없어 해당 파일을 추정해 덮어쓰지 않았다. `fragments/food-registration.html :: registeredFoods`를 현재 MyPage에 삽입하고 같은 스크립트를 한 번 로드하면 임시 목록을 공유한다. 현재 로그인 사용자별 저장이 아니다.

## 현재 상태 전이

| 동작 | 임시 선택 | 확정 등록 | 실제 섭취 이력 |
|---|---|---|---|
| 선택 | 추가 | 유지 | 유지 |
| 재클릭 해제/제외 | 제거 | 유지 | 유지 |
| 추가 확정 | 유지 | 선택된 식품만 추가, ID 중복 차단 | 유지 |
| 등록 삭제 | 유지 | 제거 | 유지 |
| 알레르기 변경 | 기존 제외 규칙 적용 | 삭제하지 않고 현재 조건 재확인 표시 | 유지 |

`smartnf.food-selection.v1`은 기존 선택 초안, `smartnf.confirmed-foods.v1`은 추가 확정한 임시 목록이다. 기존 초안을 자동 확정하지 않는다. 두 저장소 모두 현재는 같은 탭의 sessionStorage이며 계정 DB가 아니다. 현재 draft-state.js가 새로고침일 때 임시 선택 items만 초기화한다. 적용 중인 별도 제외조건과 알레르기·관리항목·확정 등록·확정 월간·저장 섭취 기록은 보존한다. 페이지 이동에서는 임시 선택을 유지한다. 검색/건강정보 정적 미확정 입력은 기본값으로 초기화하고, 적용한 알레르기 전용 입력과 저장 기록 폼은 제외한다. 건강정보에는 업그레이드된 설치 스크립트를 실행해 공통 정책을 기존 health 스크립트 앞에 연결한다.

확정 목록: version, savedAt, items[]; 항목은 id, name, confirmedAt, related, origins, demo. 식품의 원본 ID를 사용한다. 임시 확정 목록은 최대100개/24시간이며 날짜가 미래이거나 형식이 손상되면 쓰기 중단. 출처 이름은 표시용 스냅샷이고 원본 확인과 알레르기 검사는 식품 ID로 다시 수행한다.

공통 인터페이스 `SmartNFFoodRegistration.read/confirm/remove/has`와 `smartnf-food-registration` 이벤트를 사용한다. 각 페이지가 별도로 확정 배열을 만들지 않는다. 향후 read/confirm/remove를 비동기 서버 repository로 교체하고 화면은 서버가 반환한 최신 목록을 사용하도록 전환한다. 지금의 동기 `has`는 화면 캐시 조회일 뿐 서버 권한 검사가 아니다.

## Backend 구현 계약 (설계안, 이번 패키지에 API 추가하지 않음)

- GET /api/me/registered-foods: 로그인 사용자 본인의 목록 조회.
- POST /api/me/registered-foods: 선택 ID 목록의 추가 확정. 서버에서 식품 존재/알레르기/권한/중복을 재검증하고 한 트랜잭션으로 반영. ID별 추가/기존 여부와 최신 revision 반환.
- DELETE /api/me/registered-foods/{foodId}: 본인의 해당 등록만 삭제. 실제 섭취/과거 계획까지 연쇄 삭제하지 않음. 재요청에도 최종 상태 일관성 보장.
- userId는 요청 본문을 신뢰하지 않고 Spring Security 인증 주체에서 결정. CSRF 유지. 사용자+원본 식품 ID 유일성, 소유권, 낙관적 잠금/버전 충돌, 실패 rollback 검사.
- 계정 DB 저장 전 성공 문구를 표시하지 않음. 조회 실패를 빈 목록으로 덮어쓰지 않음. 실패 시 선택/등록 복원. 로그아웃/계정 전환 시 사용자 상태 정리.
- 관리항목/알레르기/식단/섭취기록은 별도 의미의 엔터티와 저장 API를 유지. 모든 종류를 한 배열에 넣거나 식품 해제로 건강 관리목표를 자동 삭제하지 않음.
- MyPage 진입/복귀/탭 포커스 시 최신 서버 조회, 저장/삭제 응답으로 표시 동기화. 여러 탭/기기에서도 DB 기준으로 일치하게 구성.

## 실제 연결에 필요한 최신 소스

현재 MyPage HTML, 해당 Controller, SecurityConfig, 회원 인증 구현, 기존 관리항목/식단 관련 API 또는 엔터티. 기존 8종 설계의 테이블/권한 결정을 확인한 뒤 연결하며 임의 테이블을 먼저 생성하지 않는다.
