# SmartNF 260: 단위 불일치 비교 추가 차단·묶음 규격 수정

## 원인과 수정
사용자 화면에서 저장 버튼뿐 아니라 비교 목록 추가도 꺼져 있었습니다. 259 코드가 필요량 단위와 상품 단위가 다르면 `add.disabled=mismatch`로 비교 추가까지 차단한 것이 원인입니다. 앞서 장보기 연결 여부만 설명한 것은 충분하지 않았습니다.

- g 필요량 화면에서도 mL·개 등의 상품을 **상품 고유 단위로 비교 목록에 추가**합니다. 단위 변경이나 필요량 환산을 전제하지 않습니다.
- 상품 카드의 규격 입력란도 요청 단위 g 대신 실제 상품의 mL/개 규격으로 표시합니다. 단위가 다를 때도 규격을 빈칸으로 숨기지 않습니다.
- 비교 목록은 상품별 단위를 유지하고 같은 단위끼리 묶어 단가·총지출 순으로 정렬합니다. 전역 단위를 바꿔도 다른 단위 상품을 삭제하거나 새 단위로 바꾸지 않습니다.
- 다른 단위의 필요량은 빈칸으로 둡니다. 이때는 판매가격·단가만 비교하고 구매 개수/잔량/총지출은 확정하지 않습니다. 목록 안에서 그 단위의 필요량을 직접 확인해 입력하면 계산과 저장 버튼을 활성화합니다.
- 비교 목록 추가와 구매상품 저장을 분리합니다. 구매 저장은 연결된 본인 장보기 항목, 실제 조회 확인ID, 상품 구성 확인 체크, 같은 단위의 필요량이 있어야 합니다. 입력한 상품별 필요량/단위가 기존 서버 저장 경로로 전달됩니다. g→mL를 자동으로 같은 값으로 넣지 않습니다.
- 저장 버튼에는 비활성 사유를 title로 표시합니다.

## 화면에서 발견한 추가 규격 오류
`서울우유 멸균 우유 1000ml · 10개`를 총1000ml로 읽던 오류를 Python·Java 양쪽에서 고쳤습니다.
- `1000ml · 10개` → 10000ml
- 19900원 상품이면 100ml당199원 (이전 1990원 표시는 잘못된 규격에 따른 값)
- x/×/* 외에 중간점·쉼표 뒤 명시적 포장 개수를 인식합니다.
- 옵션·범위·각 단위가격·모호한 개수는 계속 확정하지 않습니다. 포장 수가 명확하지 않으면 판매처 확인이 필요합니다.
- 적용 후 상품을 다시 조회해야 새 규격과 확인ID를 받습니다. 이전 조회 카드/확인ID는 재사용하지 않습니다.

## 장보기 예상가격이 계속 없는 이유
이번 변경으로 모든 미확인 예상금액을 채웠다고 판단하면 안 됩니다. 확보한 조사자료 기준:
- 올리브오일·후추·원재료 생크림: 해당 조사상품 없음.
- 정제염: 구운소금/맛소금/꽃소금은 있으나 같은 종류가 아니라 제외.
- 우유100g: mL/L 조사가격은 있으나 해당 필요량의 확인된 mL 표현이 없어 계산 보류.

259는 단위를 저장하는 구조를 추가한 것이며, 기존 g 기록에 근거 없는 개수·부피를 생성하는 기능이 아닙니다. 장보기 각 재료에 `필요량 단위 확인·수정` 링크를 추가했습니다. 우유처럼 실제 조사자료가 있는 경우 확인한 mL 필요량을 저장하거나 상품 선택 시 확인하면 같은 단위 조사금액을 사용할 수 있습니다. 나머지 품목은 실제 조사자료 확보가 남은 과제입니다. 사용자가 지정한 KAMIS·참가격 예산 정책을 임의로 판매상품 가격 대체 정책으로 되돌리지 않았습니다.

## 적용
이 ZIP은 256~260 누적본입니다. 259를 적용했다면 추가 DB 마이그레이션은 없습니다. 처음 누적본을 적용하는 경우 이전 V33이 포함되므로 MySQL 백업 및 기동 로그 확인이 필요합니다. 운영 DB/환경설정은 포함하지 않습니다.
서버 중지 → 같은 폴더 구조로 덮어쓰기 → 재시작 → 화면 새로고침 → 판매상품 재조회.

확인 순서:
1. g 필요량 상태에서 우유 검색.
2. mL 상품의 `비교 목록에 추가`가 활성화되고 목록에 mL로 들어가는지 확인.
3. 목록에서 확인한 mL 필요량을 입력. g값이 그대로 유지되는지 확인.
4. 장보기에서 연결한 경우 구성 확인 체크 후 선택·저장.
5. 1000ml·10개 상품을 재조회해 총10000ml/100ml당199원으로 표시되는지 확인.

## 검증
- Python 58건 통과.
- 관련 Node 56건 통과: 전역 g 상태에서 mL 상품 추가, 고유 단위 유지, 필요량을 임의 생성하지 않음, 확인한 mL 수량 입력 후 저장 콜백, 기존 장보기/배송비/선택 저장 회귀.
- Java 다중단위 계약 20건 및 변경 클래스 컴파일 통과. 1000ml·10개=10000ml 검사 포함.
- 기존 DB→TSV→Java 조회 격리 하네스 통과.
- Java 검증은 실제 Spring/JDBC/Jackson을 격리한 검사이며 전체 서버/DB 저장 검증이 아닙니다. 브라우저 실제 렌더링·사용자PC 저장/재조회·외부 API 재수집은 미검증입니다. 259에서 기록한 기존 번들 검사 실패와 브라우저 실행 제한도 그대로 남아 있습니다.
