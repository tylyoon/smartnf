# 영양 기준·식품 위치 통합 그래프 및 전체 재료 선택

2026-11-04 / SmartNF_GUIDE_COMPACT_LIST_UPDATE.zip 적용 프로젝트 기준.

## 반영 사항

- **영양소마다 그래프 하나**를 사용한다. 일반 기준과 질환별 관리 기준의 숫자·단위가 같으면 기준점 하나에 ‘일반·질환별 관리 기준’으로 합친다. 서로 다른 수치면 동일 눈금에 두 기준점을 표시한다.
- 2번 식품 선택 기준에는 기준점만 표시한다. 3번 선택한 식품 상세에는 같은 그래프에 **주황색 마름모 ‘이 식품’** 위치를 추가한다. 일반 기준은 파란 실선, 관리 기준은 초록 점선, 통합 기준은 초록 실선으로 구분하고, 아래에 이름과 정확한 수치를 표시한다. 실제 섭취량이나 좋음/나쁨 점수가 아니다.
- 함량이 기준보다 커도 잘라서 끝에 붙이지 않고 눈금 범위를 확장해 실제 위치를 표시한다. 수치 0은 원점에 표시하고 결측·미량·미측정은 임의로 0 위치에 놓지 않는다.
- 단위가 다른 총열량 %와 g은 한 눈금으로 환산하지 않는다. 포화지방의 총열량 7% 기준 등은 문구로 유지한다. 비교할 고정 수치 기준이 전혀 없는 성분은 함량과 관리 요령만 표시하며 임의 눈금을 만들지 않는다.
- **전체 재료 선택 / 전체 선택 해제 / 선택한 재료 ○개·전체 ○개**를 공통 레시피 선택기에 추가했다. 건강별 식품 선택 가이드와 식재료·식품 영양정보 모두에 적용된다.
- 전체 선택·해제는 체크 상태만 변경한다. **기존 ‘이 참고 레시피·선택 재료 연결’ 버튼을 눌러야 선택 식재료 묶음과 저장 요청에 반영**된다. 기존 연결이 있으면 연결 전까지 유지한다. 음식 선택 선행, 알레르기/자료 검토 보류, 원문 버전·재료 인덱스 검증은 유지한다.
- 참고 레시피 재료의 전체 선택은 실제 음식 전체의 성분 확정이 아니며 영양값 자동 재계산·실제 섭취 등록은 하지 않는다.

## 적용

1. 실행 중인 서버에서 Ctrl+C.
2. ZIP 내부 `src`, `docs`를 프로젝트 루트에 병합.
3. **`bash run_local.sh`** 실행.
4. 브라우저 **Ctrl+F5**.

이번에는 새 DB migration, Java 수정, npm 빌드, 영양자료 재수집이 없다. 기존 V13과 계정·동의·건강관리 계획 구조를 유지한다. 자동 서버 테스트 명령은 `./gradlew.bat test`이며 서버 실행 명령과 구분한다.

## 화면 확인 순서

1. 혈압 관리 → 2번 나트륨의 일반·관리 기준이 하나의 기준점으로 합쳐지는지 확인.
2. 음식 ‘느타리버섯볶음’ 선택 → 나트륨 그래프에서 기준점과 이 식품 함량 위치가 한 그래프에 보이는지 확인. 범례의 이름·수치를 함께 확인한다.
3. 레시피 있는 음식 담기 → 레시피 열기 → 전체 재료 선택/해제와 개수 표시 확인.
4. 전체 선택만 했을 때는 기존 연결이 유지되고, 연결 버튼을 누른 뒤 선택 식재료에 반영되는지 확인.
5. 식재료·식품 영양정보에서도 레시피 있는 음식(예: 호박죽)을 선택해 같은 기능 확인.
6. 필요한 재료를 연결한 뒤 날짜·계획 구분을 확인해 MyPage에 저장하고 계정에서 상세를 확인한다.

## 검증

- Node 21개 통과: 숫자/단위/결측/0 처리, 동일 기준 병합, 다른 기준의 위치 순서, 초과 함량의 눈금 확장, 영양소당 단일 그래프, 비교 기준 없는 성분의 함량 표시, 기존 레시피·조건 보류 회귀.
- 변경 JS 문법 검사 통과.
- Chromium 실제 HTML 템플릿·JS·JSON + 가상 API: 가이드와 영양정보 두 화면에서 전체 선택→해제→다시 전체 선택→연결, 연결 전 저장 대상 불변, 연결 후 모든 인덱스 반영을 확인했다. 가이드의 음식별 묶음·재료 제외/재연결·저장 payload와 건강관리 달력 회귀도 확인했다.
- 가이드 320/390/800/1440px, 영양정보 320/390/1440px 가로 넘침 없음. 모바일 상세 패널과 JS 오류 없음 확인.
- 실제 Spring/MySQL 저장·재로그인은 가상 API 검증과 별도이며 사용자 환경 확인 대기다. 서버·DB·계정·동의 정책을 변경하지 않았다.
