# 현재 MyPage의 나의 건강정보 조회·수정·저장 이력

2026-11-04. 오늘의 선택 업데이트(141절) 및 마지막 건강정보 업데이트 원상복구(143절)까지 적용된 프로젝트 기준입니다.

## 적용
1. 실행 중인 서버를 종료합니다.
2. ZIP 안의 src/frontend/docs를 프로젝트의 같은 경로에 병합합니다. 상위 포장 폴더는 없습니다.
3. `bash run_local.sh`로 다시 시작하고 Ctrl+F5를 누릅니다.
4. 생성된 personal-mypage.js를 포함하므로 사용자 PC에서 npm 빌드는 필요하지 않습니다. 새 테이블·migration·DB 삭제/변환 SQL은 없습니다.

## 이제 어디에서 확인하나요?
**현재 MyPage 왼쪽 메뉴 → 나의 건강정보**
- 최신 건강정보: 본인 계정 DB의 최신 저장본과 저장일을 표시합니다. 입력해 저장한 항목만 분류별로 보여주며, 미입력은 정상/0으로 바꾸지 않습니다.
- 건강정보 수정: 저장값이 채워진 입력란에서 수정하고 확인 체크 후 변경사항 저장을 누릅니다. 서버 원본 필드 정의·옵션·범위와 같은 API를 사용합니다.
- 저장 이력: 과거 저장 시각을 선택해 당시 값을 조회합니다. 과거 조회는 현재 저장본을 덮어쓰지 않습니다. 20건 단위로 이전/다음 이력을 조회합니다.
- 저장 동의·삭제 관리: 일반 조회/수정과 분리했습니다. 동의 철회·전체 건강기록 삭제는 접힌 영역에서 범위와 최종 확인을 거칩니다. 개별 저장본 삭제 기능으로 표현하지 않습니다.

기존 /mypage/health, /mypage/health/history, /mypage/consent도 현재 MyPage 셸과 왼쪽 메뉴를 유지합니다. 이전 health/mypage 화면으로 연결하지 않습니다. /mypage 자체의 대시보드, 선택 식품/장보기/외식, 식사, 실천, 설정 메뉴는 유지합니다. /health/info는 원래 헬스케어 계정 입력 화면으로 유지하며 같은 프로필 API/DB를 사용합니다. 142절의 공개 체험 자동 복원 경로는 되살리지 않습니다.

기존 계정 저장본이 없으면 명확히 빈 상태와 입력 버튼을 표시합니다. 과거 브라우저 임시 입력을 계정 저장본으로 간주하거나 자동 업로드하지 않습니다. 알레르기를 새로 저장·복원하거나 개인 진단·목표를 자동 처방하지 않습니다.

## 저장과 개인정보 처리
- 기존 /api/me/health의 consent/profile/catalog/history/profiles API를 사용합니다. 사용자 ID를 브라우저가 지정하지 않습니다.
- 저장 시 최신 profile ID와 consent event, UUID를 전달합니다. 409 충돌은 강제 덮어쓰기하지 않고 다시 조회하도록 안내합니다.
- 결과가 불확실한 저장 오류는 입력을 유지하고 같은 요청 ID로 다시 시도합니다. 수정 중 메뉴 이동/페이지 이탈에는 확인을 둡니다.
- 본문과 과거 기록 조회 전후 동의를 재확인하고, 계정 전환·권한 거절·동의 변경 시 민감정보를 지웁니다. BFCache 복귀 시 다시 조회합니다. 기존 no-store/CSRF/소유권 검증을 유지합니다.
- 건강정보 수정은 새 버전으로 저장합니다. 관리항목은 재검토를 안내하며 자동 확정하지 않습니다. 기존 선택 식품·계획은 자동 변경하지 않습니다.
- 동의 철회는 기존 서버 정책대로 건강정보·질환/측정/관리항목·일일·식사 기록을 모두 삭제합니다. 회원 계정·동의 이력과 별도 식품/계획은 유지됩니다. 재동의해도 삭제한 기록은 복원되지 않습니다.

## 검증
- Java21/Gradle9.8.1/Spring Boot4.1.1 실제 프로젝트 컴파일 및 관련 서버 테스트 35개 통과: CurrentMyPageHealthTests 1개(4개 경로의 현재 셸/no-store 검증), HealthStorageTests 22개, FoodPlanTests 12개. 검증 환경의 Mockito 동적 에이전트 부착 제한은 테스트 JVM의 명시적 ByteBuddy agent로 해결했으며 제품 코드/테스트 검증을 우회하지 않았습니다. 이전 작업의 전체 서버 미실행 상태와 구분합니다. 이번에도 프로젝트 전체 테스트를 모두 실행한 것은 아닙니다.
- frontend 데이터 테스트 20개(신규 건강정보 3개 포함), 기존 JS 41개, React 빌드 통과.
- 실제 템플릿/최종 React 번들 + 가상 API Chromium: 메뉴→최신 조회→수정/확인 저장→과거 이력→동일 ID 오류 재시도→충돌→빈 계정→계정 변경 스크럽→별도 철회/재동의/새 입력을 확인했습니다. HTML 문자열 안전 표시, 0/미입력 구분, 이탈 취소, 320/390/800/1440px 편집 가로 넘침·JS 오류 없음도 확인했습니다.
- 실제 Spring Boot/Security/Thymeleaf + 별도 H2 서버와 Chromium: 테스트 계정 로그인, 동의/CSRF, 첫 저장, 수정으로 새 버전 생성, 4개 경로에서 현재 셸/no-store 유지, 과거 저장본 조회, 헬스케어 /health/info의 같은 값 복원, 새 브라우저 로그인 세션의 최신값 복원, 4개 화면 폭 및 JS 오류 없음을 확인했습니다.
- 사용자 PC의 MySQL과 실제 계정에는 접근하지 않았습니다. 적용 후 기존 저장값이 보이는지 사용자의 실제 환경에서 확인해야 합니다. 저장값 유무를 임의로 단정하거나 복원했다고 표현하지 않습니다.
