# SmartNF 건강정보 저장·MyPage 적용 안내

2026-10-28 · 회원별 건강정보/관리항목 저장 1차 구현본

## 먼저 적용하기

1. 실행 중인 서버를 Ctrl+C로 종료합니다. 개발 DB의 기존 기록이 중요하면 먼저 본인 관리 절차로 백업합니다.
2. SmartNF_HEALTH_STORAGE_UPDATE.zip을 풉니다. 안의 src/와 docs/를 build.gradle이 있는 프로젝트 루트에 덮어씁니다. 추가 smartnf 폴더를 만들지 않습니다.
3. 기존 .env.local과 run_local.sh는 유지합니다. 이번에 추가할 환경변수는 없습니다. 과거 인증 ZIP으로 다시 덮어쓰지 마세요.
4. 프로젝트 루트에서 실행합니다.

```bash
bash ./gradlew test --no-daemon
```

이전 일반·SNS 테스트에 건강 저장 통합 테스트를 추가했습니다. 테스트는 별도 H2 메모리 DB를 쓰고 Flyway를 끄므로 운영 MySQL에 건강 기록을 생성하거나 삭제하지 않습니다. Java21과 기존 Gradle 환경이 필요합니다.

이 전달 환경에서는 독립 Java 입력 검증·JS 모의 검사·관계형 제약 모의 검사만 실행했습니다. Gradle 다운로드 services.gradle.org DNS 실패로 전체 JUnit/MySQL 마이그레이션을 실행하지 못했고, Chromium 실행 파일 부재로 실제 브라우저 화면 검사도 완료하지 못했습니다. BUILD SUCCESSFUL과 사용자 PC 동작 확인이 완료 기준입니다.

## 서버와 DB 확인

테스트 성공 후:

```bash
bash run_local.sh
```

Flyway V5가 다음 내용을 추가합니다. 기존 V1~V4 파일과 회원·SNS 데이터는 변경하지 않습니다.

- 건강정보 확정 버전/질환 상세/측정값 3개 테이블.
- 행동/평가 분야/허용 조합 마스터 3개 테이블.
- 회원 관리항목 확정본/행동/분야 연결 3개 테이블.
- HEALTH_DATA 개발 안내 문서 1개.

기존 7개 테이블(회원6+Flyway)에 9개가 추가되므로 다른 테이블이 없다면 총16개입니다. V5 실행은 건강 기록 저장 동의나 기존 임시정보 자동 업로드를 수행하지 않습니다.

MySQL은 기존 앱 계정으로 조회하면 됩니다.

```sql
USE smartnf;
SELECT version, description, success
FROM flyway_schema_history ORDER BY installed_rank;
SHOW TABLES;
```

V5의 success=1을 확인합니다. 최신 이력이 V4 다음이라는 가정에 기반하므로 본인이 따로 추가한 V5가 있으면 덮어쓰지 말고 충돌 내용을 알려주세요. DB 권한 오류가 발생하면 마이그레이션 계정/앱 계정의 해당 오류 메시지를 확인합니다. 루트 계정으로 앱을 실행하거나 무조건 전체 권한을 부여하지 않습니다.

## 실제 확인 순서

1. 이메일 또는 SNS로 로그인합니다. 상단 MyPage는 이제 실제 회원 페이지입니다. MyPage 체험은 별도 가상 화면으로 유지됩니다.
2. http://localhost:8080/mypage 를 Ctrl+F5로 새로고침하고 개발용 건강정보 저장 안내를 확인하고 저장 동의에 체크한 뒤 저장 동의를 누릅니다. 로그인 방식에 따라 서로 다른 SmartNF 회원이면 각각 별도 동의·기록입니다.
3. http://localhost:8080/health/info 를 엽니다. 로그인 전용 입력 화면입니다. 공개 /preview/health/info에서는 기존처럼 계정 DB에 저장하지 않습니다.
4. 직접 가상 건강정보를 입력합니다. 예: 키170, 체중70, 고혈압 선택 후 진단월2020-05. 자동 ‘가상 예시 채우기’ 데이터는 그대로 DB에 저장할 수 없습니다.
5. ‘회원 계정에 건강정보 저장’ 영역에서 입력 확인에 체크하고 계정 저장 버튼을 누릅니다. ‘나의 건강정보 확정’/‘브라우저 임시 확정’은 기존 같은 탭 임시 확정이므로 DB 저장과 구분합니다.
6. 계정 저장 성공 시 화면이 제출 내용과 같으면 브라우저 임시 확정도 맞춥니다. 요청 중 추가로 입력한 내용은 자동 확정하지 않습니다. 새로고침 후 계정 저장본과 진단월이 복원되는지 확인합니다. 로그아웃→재로그인 후에도 같은 회원의 저장본을 확인합니다.
7. 비교·평가에서 ‘내 입력 결과 보기’로 바꾸고 맞춤 관리항목을 선택합니다. 기존 ‘선택한 관리항목 확정’ 버튼으로 먼저 임시 확정합니다. 그다음 아래 ‘확정한 관리항목을 계정에 저장’ 영역에서 확인 체크 후 계정 저장합니다.
8. /mypage 에서 입력값과 저장일, 측정일, 관리항목/분야를 확인합니다. 입력 수정·저장은 새 버전을 만들며 저장 이력에서 예전 입력을 조회할 수 있습니다.
9. 건강정보를 변경해 다시 저장하면 기존 관리항목은 ‘재확인 필요’로 남습니다. 새 입력 기준으로 항목을 재확정·저장합니다. 전체 해제 버튼으로 현재 관리항목을 비우는 확정본도 저장할 수 있습니다. 이전 이력은 DB에 보존합니다.
10. 다른 회원으로 로그인해 이전 계정 기록이 보이지 않는지 확인합니다. 같은 이메일을 가진 다른 SNS 계정도 자동 병합하지 않습니다.
11. 동의 철회/삭제 검사는 지워도 되는 가상 기록으로만 진행합니다. MyPage의 철회 버튼에는 삭제 전 확인 창이 표시됩니다. 실행하면 해당 회원의 이 기능 전체 건강정보·관리항목 이력이 삭제되고 회원 계정은 유지됩니다. 재동의해도 복원되지 않습니다.

개인 기록을 담은 전체 DB 결과나 화면을 채팅에 보낼 필요는 없습니다. 정상/실패와 비밀값·건강 원문을 제외한 오류 메시지만 알려주세요.

## 저장 실패와 다른 탭

- 저장 실패/응답 시간 초과: 입력을 유지합니다. 같은 내용 재시도에는 같은 requestId를 사용해 중복 저장을 방지합니다. 상태 변경/다른 탭 선행 저장은 충돌로 거부하므로 최신 기록을 확인하세요.
- 동의 상태가 변경된 오래된 요청: 동의 이벤트 ID로 거부합니다. 철회→재동의 후 과거 요청을 재전송해 삭제된 기록을 되살리지 않습니다.
- 계정 전환: 회원 ID는 서버 인증 주체에서 결정합니다. 오래된 탭의 계정 표시가 다르면 거부합니다. 관리자도 본인 기록만 접근합니다.
- BroadcastChannel 지원 브라우저에서는 동의 변경을 다른 탭에 값 없이 알리고 관련 임시 정보를 정리합니다. 미지원 환경도 API의 소유권·동의 검사를 통과해야 저장할 수 있습니다.

## 이번 범위와 남은 작업

구현 범위: 건강 입력87개 이름의 허용 목록/타입 검증, 건강 측정19개, 진단월 보존, 다분야 관리항목·해제/재선택, 회원별 원자적 저장/중복 요청/충돌/별도 동의, MyPage 최신본·프로필 이력, 다른 회원·정지·미동의 접근 차단.

운영용 동의/정확한 보유기간/백업 삭제/탈퇴 정책은 미확정이며 개발 안내만 제공합니다. 알레르기·식사/선택식품 영구 저장, 전체 관리항목 변경 이력 UI, 체중 차트·변화 평가·실천 통계·AI 리포트는 후속입니다. 기존 식품 가이드는 같은 탭의 유효한 임시 확정 목록을 계속 사용하며 DB 조회만으로 개인 추천이 검증된 것은 아닙니다.
