# SmartNF 전체 자료 분석 및 서비스 활용 목록

작성일: 2026-10-27 / 분석 대상: 현재 전달받아 원본 확인이 가능한 자료 전체 / 화면·DB·추천 규칙 변경 없음

## 1. 분석 결론

전체 24,797개 레코드(건강 658 + 식재료 3,366 + 음식 19,617 + 레시피 1,156)를 빠짐없이 구조·분류·결측·중복·연결 가능성 관점으로 검사했다. 최신 영양 엑셀의 137열·160열도 전수 프로파일링했다. 원본 재검사로 만든 JSONL이 현재 화면 데이터의 입력 해시와 일치했고, 영양 청크의 해시 및 건강 XML-JSON 무결성도 검사했다.

**이번에 완료한 것은 전체 레코드의 데이터 품질 분석과 서비스 활용 설계다. 모든 본문 문장을 의학적으로 검토하거나 모든 음식을 질환별 추천으로 승인한 것은 아니다.** 제목·본문의 키워드, 재료명 일치, 이름 중복은 검토 후보로 사용하며 개인 적합성으로 해석하지 않는다.

먼저 활용 가능한 것은 식품 검색·영양값 표시, 기존 레시피 재료·조리 안내다. 질환별 추천·개인 영양 계산·월간 최적화·예상 효과는 별도 근거 연결과 검증이 필요하다. 화면을 더 추가하기 전에 아래 보완 순서대로 데이터 기반을 정리하는 것이 적절하다.

## 2. 범위와 원본

| 자료 | 레코드 | 실제 확인 범위 | 이번 완료 범위 |
|---|---|---|---|
| 건강정보 | 658 | 저장 JSON/XML 658쌍, 제목·절·원본 해시 | 전체 절별 주제·역할 후보, 중복·부분 승인 대조 |
| 식재료 | 3,366 | 국가표준식품성분표 10.4, 137열 | 전체 열 보유율, 원본 20분류, 현12영양필드 품질 |
| 음식 | 19,617 | 20260828 음식DB, 160열 | 전체 열 보유율, 원본25분류, 단위·동일명·결측 |
| 레시피 | 1,156 | 원문 재료·분량·방법·단계·영양5필드 | 모든 레시피 품질, 재료구간·코드후보·연결 검사 |

- RDA 파일에는 과거 10.0~10.3 시트도 있다. 현행 서비스 기준은 기존 결정대로 **10.4**를 유지하고 과거 버전은 현행 건수에 중복 합산하지 않았다. 과거 시트는 목록·크기를 기록했으며 세대별 영양값 변화 비교는 이번 범위에 포함하지 않았다.
- 가공식품 전용 원본, 건강기능식품 원본, 별도 해양수산 원본은 현재 접근 가능한 업로드·자료 패키지에서 확인되지 않았다. 사용자 PC에 없다는 뜻이 아니다. 따라서 해당 DB까지 분석 완료했다고 말할 수 없다.
- `data.zip` 업로드는 로컬 ZIP 중앙 디렉터리를 읽을 수 없는 상태여서 재압축하거나 수정하지 않았다. 이전에 검증·복원한 658쌍의 JSON/XML을 직접 다시 검사했다.
- 신청 688건, 브라우저에서 관찰한 부분 승인 목록 668건, 확보 본문 658건은 서로 다른 집합이다. 숫자 차이만으로 누락 ID를 추정하거나 688건 전체 수집 완료로 간주하지 않는다.
- 원본 본문·API TOKEN·비밀번호는 이 보고서나 분석 패키지에 포함하지 않았다. 건강 절 색인은 ID·제목·절 위치·검색어만 기록했다.

## 3. 우선 확인해야 할 문제

### 3.1 제목이 다른데 본문이 같은 건강자료

| 묶음 | ID와 제목 | 판단 |
|---|---|---|
| 1 | 5283 홍역, 볼거리, 풍진 / 6759 사람면역결핍바이러스 | 절 제목·본문 목록이 완전히 같음. 원본 공통 자료인지 대응 오류인지 재조회·대조 필요 |
| 2 | 6807 전해질 이상(저칼륨혈증) / 6808 전해질 이상(고칼륨혈증) / 6809 전해질 이상(고나트륨혈증) | 절 제목·본문 목록이 완전히 같음. 원본 공통 자료인지 대응 오류인지 재조회·대조 필요 |

XML 해시가 맞는다는 것은 저장 이후 파일이 일치한다는 뜻이다. 제목과 본문의 의미까지 올바르다는 보장은 아니다. 특히 서로 다른 질환 제목은 본문 대응을 확인하기 전 개인화 근거로 사용 보류하는 것이 적절하다. 이번 감사에서는 운영 데이터를 삭제하거나 자동 차단 규칙을 바꾸지 않았다.

부분 승인 목록에서 관찰되지 않은 ID는 **5283, 6808, 6809**다. 승인 거절을 의미하지 않으며 전체 승인 목록과 별도 대조해야 한다.

### 3.2 본문 언급과 주제를 구분해야 함

기존 광범위 분류는 내용에 단어가 한 번 언급되어도 해당 주제에 포함한다. 예를 들어 고혈압 약의 부작용이나 감별진단에서 특정 영양소가 언급됐다는 이유만으로 식품 추천 근거가 될 수 없다. 이번에는 제목 주제 / 본문 언급 / 제목에는 없는 본문 언급을 구분했다.

|---|---|---|---|
| 혈압 | 12 | 267 | 256 |
| 혈당·당뇨 | 14 | 255 | 241 |

모두 복수 집계이며 제목 키워드도 분류 후보일 뿐이다. 예를 들어 신증후군출혈열처럼 문자열은 겹쳐도 대상 질환이 다른 사례가 있어 검토가 필요하다. 12,658행의 절별 주제 색인을 제공해 어느 절에서 단어가 발견됐는지 추적할 수 있게 했다. 비어 있는 정제 절 2,836개에는 이미지 URL만 있는 절·위젯 제거 등이 포함되므로 본문 전체가 공란이라는 뜻이 아니다.

### 3.3 음식 수와 실사용 메뉴 수는 다름

음식 DB는 빵·과자류 8,643건, 음료·차류 5,776건을 포함한다. 서로 다른 브랜드·제품·제공처가 섞여 있으므로 19,617건 전부를 서로 다른 식사용 추천 메뉴로 볼 수 없다. 같은 이름이 있는 묶음은 1,737개이며 관련 레코드는 5,707개다. 이름만으로 합치지 않고 코드·출처·기준량을 유지해야 한다.

재료 후보가 한 개라고 자동 확정하지 않는다. 생것/삶은것, 부위, 양념 제품, 가정단위, 공동 분량 등을 확인해야 한다. 레시피를 정확히 재현하지 않는 일반 식품명 대응은 기준 설명에 사용할 수 있어도 실제 레시피의 영양 합계에는 사용할 수 없다.

기존 통합 파이프라인의 **검토 묶음 2,590개(후보 없음1,888 / 다중560 / 단일 미확정142)**는 재료 구간 13,059개를 묶은 수다. 서로 집계 단위가 다르므로 위 표와 혼동하지 않는다.

### 5.2 현재 서비스의 105종 위치

현재 추천 데이터는 식재료105 + 표준음식5 + 추천 재료 활용 레시피105 = 총215개 후보다. 레시피105종은 채소45·두부38·생선14·기타반찬8이며 전체1,156개 중 일부다. 이번 분석은 나머지1,051개도 포함한다. 다만 전수 검사했다고 모두 새 추천으로 등록한 것은 아니다.

이 105종은 추천 대상 재료를 활용한 음식이라는 연결 근거를 가지며, 완성 음식 전체의 질환별 적합성이 검증됐다는 뜻이 아니다. 영양기준·알레르기·분량·복합질환 검토를 통과한 범위만 향후 확대한다.

## 7. 정보 확보와 검토 순서

### P0 — 원본 대응과 범위 확정

1. 건강 본문 중복 5개 ID를 공식 API 응답과 화면의 제목·ID·본문으로 각각 대조한다. 단순 재다운로드로 기존 원본을 덮어쓰지 않고 새 실행폴더에 저장해 차이를 비교한다.
2. 승인 688건 전체 목록을 확보해 부분 목록 668건과 본문 658건의 실제 차집합을 만든다. 공란 응답은 실패 사유를 유지하며, 688-658=30건이라는 계산만으로 누락을 확정하지 않는다.
3. 사용자 PC의 가공식품·건강기능식품 다운로드 파일 이름·버전·건수를 확인한다. 파일이 확보되면 이 보고서 범위에 추가한다. 별도 수산물 원본이 없더라도 RDA의 어패류683·해조류53건은 이미 포함돼 있으므로 겹침을 대조한 뒤 추가 수집한다.

### P1 — 기존 데이터 활용 준비

4. 건강자료에서 식사요법·생활습관·주의사항을 가진 절을 먼저 검토한다. `condition_id / source_id / section_id / 원문위치 / 적용대상 / 제외조건 / 영양소 / 행동항목 / 검토상태 / 갱신일`로 근거표를 만든다. 단어 빈도는 검색 순서에만 활용한다.
5. 재료 검토 묶음2,590개를 재사용 빈도·연결 레시피 수·명확성 기준으로 정렬한다. 원문 재료의 상태·부위·제품 여부를 확인하고 ‘확정/여러 후보/정보 부족’을 남긴다. 원문과 선택 코드, 검토 이유를 함께 보존한다.
6. 비어 있는 값은 먼저 원본 API·엑셀의 기존 필드로 보완 가능한지 확인한다. 없는 값은 0으로 채우거나 LLM으로 만들어 넣지 않는다. 부족한 자료만 공식 제공처의 추가 DB/API·공식 조리자료에서 확보한다.
7. 100g·100ml·가식부·1인분·전체 배합을 구분한 단위 사전을 작성한다. 가정단위 환산·밀도·수율·가식부 기준이 없으면 계산 보류 상태를 유지한다.

### P2 — 서비스 규칙과 검증

8. 근거와 영양값이 연결된 후보부터 추천 테스트셋을 만든다. 질환별·복합질환별·알레르기별·미입력별로 포함·제외 이유를 확인한다. 현재 미입력 진행 허용 정책을 임의로 바꾸지 않는다.
9. AI 레시피·식단은 확정된 코드·분량·목표량에 기반해 식단 제약을 검증하는 별도 단계로 개발한다. 건강 식생활 가이드는 기존 레시피 활용 안내 역할을 유지한다.
10. 네이버 장소 정보는 건강정보 DB와 별도 데이터다. 지도 연계와 외부 장소 검색 설정을 확인하고, 매장 메뉴·영업정보·실제 조리법을 구분한다. 이번에는 외부 API를 호출하거나 지도 설정을 변경하지 않았다.
