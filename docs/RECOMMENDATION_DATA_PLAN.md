## 실제 처리 순서
1. 원본 출처ID/절/개정일/해시와 선택 기준을 검토표에 연결.
2. 필요한 추가 필드의 공개 제공 여부·신청 필요·이용조건 확인. API는 정식키, 파일은 공식 다운로드, 비공개 표는 허가 전 미수집.
3. Python으로 식품코드·조리 상태·중량·성분을 정비. 추정값은 확정하지 않음.
4. 규칙의 적용대상/제외조건/충돌 우선순위 검증. 알레르기/개별제한 우선, 미지원질환이 공존하면 전체 자동 추천 보류.
5. 화면에 추천 이유·연결 조건·원본 성분과 보류 이유/확보 방안을 함께 제공.

## 현재 구현 범위
- 건강정보의 확정 conditions/weightGoal/targetWeight/기간/medication/restriction을 텍스트 표시. 알레르기는 별도 확정 프로필을 읽음. 관리항목을 임의 변경·저장하지 않음.
- 보유 RDA의 원재료/두부 등 최대6개 후보를 공식 일반 식품군 방향과 연결. 미지원질환/입력된 개별지침/소아 조건 등은 보류. 일반 식품군 후보와 정량 치료식 추천은 다름.
- 사용자가 선택하면 공통 선택 목록에 추가, 다시 선택하면 제외 및 추천 카드 제거. 영양정보 페이지 직접 선택과 같은 저장 계약 유지.

## 추천 근거 마련과 재개 조건 (최신)
1. 제공 범위 정의: 일반 식품 선택 지원과 질환별 치료식/분량 처방을 구분한다. 입력한 질환/목표별로 어떤 판단까지 제공할지 정한다.
2. 공식 자료 확보: 보유 KDCA658건에서 질환별 식사 근거의 정확한 절/표/적용대상/제외조건/개정일을 추출한다. 일반 권장 식품군을 단독 근거로 개별 식품의 임상 적합성을 선언하지 않는다. 추가 전문기관 표는 공개·재사용 조건 확인 후 파일/API/허가된 수동정리로 확보한다.
3. 선정 기준 문서화: source_id/절/개정, 적용조건, 식품군, 비교할 영양소, 비교 기준량, 수치 또는 정성 기준, 제외조건, 부족데이터시 보류, 규칙 검토상태 기록. 원문이 하루 전체 섭취 기준이면 이를 식품100g 합격 기준으로 전용하지 않는다. 근거 없는 임계값/가중치/‘건강점수’ 생성 금지.
4. 식품 단위 증거 연결: 검토된 코드·생것/조리상태·원재료·실제 중량·영양값과 단위를 연결한다. 식품군 수준 근거와 개별 식품 근거의 강도를 구분. 빈칸을0으로 처리하지 않는다. 이름 검색 일치만으로 추천 확정 금지.
5. 복합조건 검증: 알레르기/개인 제한 우선. 병행 질환·복약·검사·영양목표 충돌 시 보류하고 부족 입력을 알린다. 기존 선택 목록을 추천 중단으로 삭제하지 않는다.
6. 검토/테스트: 영양·의료 전문가가 필요한 범위의 기준은 실제 검토를 받아야 하며 AI/개발자 문서 확인을 전문가 승인으로 표시하지 않는다. 대표/경계/결측/복합질환/알레르기 사례 검증 후 검토된 범위만 공개한다.
7. 사용자에게 ‘이 조건 때문에, 이 기준에서, 이 식품이 해당한다’는 근거를 설명할 수 있을 때 추천 재개. 출처 변경시 재검토하고 근거 버전과 식품데이터 버전 보관.

당장 할 작업: 보유 원문의 질환별 근거표 작성과 누락 목록 확정. 그 표가 먼저이며 추천카드/점수부터 만들지 않는다. 신규 인증키 신청은 확인된 데이터 필드가 필요한 경우에만 요청한다.
