# SmartNF 259: 재료별 다중 단위와 상품 카드 버튼 개선

## 적용 전 확인
이번 누적 ZIP에는 **V33 MySQL 마이그레이션**이 포함됩니다. 기존 scheduled.sqlite 백업과 별도로 MySQL smartnf DB를 백업하고 서버를 중지한 뒤 덮어쓰세요. 서버 기동 시 Flyway V33 성공을 확인해야 합니다. 운영 DB 파일과 인증키는 ZIP에 넣지 않았습니다. 실제 DB 마이그레이션은 이 환경에서 실행하지 않았습니다.

## 재료별 다중 단위
- 같은 재료에 확인된 g·mL·개·팩·봉·병 수량을 함께 저장합니다. 개수/포장 수를 중량이나 부피와 같은 값으로 간주하지 않습니다. kg→g, L→mL는 같은 차원 내 정확한 단위 변환입니다.
- 예: 계란 2개와 실측/표시 근거의 100g을 같이 보관할 수 있습니다. 한 재료의 서로 다른 수량 표현이며 예상금액은 계산 가능한 조사 단위 하나만 사용합니다.
- 근거 없는 밀도나 계란 1개 중량은 만들지 않습니다. 사용자가 확인한 수량에는 원문/표시/실측 등의 근거를 함께 입력합니다.
- 기존 g 기록을 유지합니다. 중량을 모르는 개수·부피 재료는 grams=NULL이며 영양 계산용 g를 임의로 채우지 않습니다. 영양 계산은 기존대로 확인된 g가 필요하며 없으면 자료 부족/입력 확인 대상으로 남습니다.
- 레시피 원문의 g/kg/mL/L/개/알/판/팩/봉/병을 파싱해 수량을 보존하고 인분 변경 시 같은 비율로 조정합니다. 식단 계획 입력·스냅샷에 원문 단위 메타데이터를 추가해 저장/복원 경로에 전달합니다. 기존 g 전용 계획의 해시 표현은 별도로 유지했습니다.
- 기존 g만 있는 레시피를 임의로 개/mL로 소급 변환하지 않습니다. AI 레시피 생성 요청의 기존 g 제안 규칙은 유지하며, AI가 밀도·계란 중량을 추정해 새 단위를 만드는 작업이 아닙니다.
- 같은 재료의 여러 레시피 기여분을 합칠 때 전체 기여분이 확인된 단위만 합계로 사용합니다. g만 아는 부분과 개만 아는 부분을 환산할 수 없으면 단위별 행으로 보존하며 누락시키거나 섞어 더하지 않습니다.

## 저장과 계산 경로
- ShoppingListModels.Item에 quantities(amount/unit/evidence)를 추가하고 기존 3개 인자 생성자를 유지합니다. 중복 단위·잘못된 수량·근거 누락을 검증합니다.
- V33: shopping_item_quantities 테이블 추가, shopping_list_items.grams와 shopping_product_choices.required_grams에 NULL 허용, 구매 단위 열 길이 확장. 기존 값을 삭제하거나 단위 환산값으로 덮어쓰지 않습니다.
- 장보기 저장/재조회·수정·삭제 및 멱등 해시에 단위 정보를 연결합니다. 회원 소유권과 목록 revision을 유지합니다.
- MyPage 장보기 수정 화면에서 `확인한 단위 추가`로 다른 단위 수량과 근거를 저장할 수 있습니다. 입력 후 변경 저장을 눌러야 합니다. 영양 중량(g)과 같은 수량을 다른 단위로 표현한 값인지 사용자가 확인해야 합니다.
- 장보기 조사 예상금액은 KAMIS·참가격의 g/mL/개 등 확인 가능한 단위 하나를 골라 계산합니다. 판매가격으로 예상금액을 대체하지 않습니다. 단위 확장만으로 없는 조사 품목이 생기는 것은 아닙니다.
- 실제 업로드 KAMIS 계란 규격은 `계란(10구) · XL10구`처럼 개수가 반복 표기됩니다. 동일 개수의 반복 라벨은 한 번만 인식하고 서로 다른 개수의 모호한 표기는 확정하지 않도록 처리했습니다.
- 상품명에 `계란 10개 (500g)`처럼 둘 다 명시된 경우 각 단위를 인식합니다. g 기준이나 개 기준으로 조회·비교·선택할 수 있고, 서버 확인ID 검증도 상품에 명시된 단위/총량 중 일치하는 값을 요구합니다.
- `난각번호 1번`을 계란 개수로 오인하지 않습니다. 계란 1개 무게, 한 판의 알 수 등은 명시 없이 추정하지 않습니다. 판매포장 개수는 정수로 검증합니다.
- 단가는 g/mL는 100단위당, 개/팩/봉/병은 1단위당 표시합니다. 포장 단위끼리 비교할 때도 실제 구성·규격이 같은지 판매처에서 확인해야 합니다.

## 버튼·화면
- 상품 카드의 수량 입력과 확인 체크박스를 분리하고 체크박스 옆에 확인 문구를 배치했습니다.
- `비교 목록에 추가` / `이 상품 선택·저장` / `판매처에서 확인`을 별도 액션 행으로 정리했습니다.
- 버튼 높이 44px 이상, 간격 10px, 보조/주요/판매처 링크 색상 구분, 키보드 포커스 표시를 적용했습니다. 비활성 버튼은 별도 배경·텍스트로 구분합니다.
- 600px 이하에서는 버튼을 한 줄씩 세로로 배치합니다.
- 실제 브라우저 렌더링을 시도했으나 Chromium 시작 시 socket() Operation not permitted로 중단됐습니다. 외관/모바일 겹침은 적용 후 사용자 화면으로 확인해야 합니다.

## 적용 후 순서
1. MySQL 백업 → 서버 중지 → 프로젝트 최상위에 누적 ZIP 덮어쓰기 → 서버 기동.
2. 기동 로그에서 V33 성공을 확인합니다. 실패하면 로그를 확인한 뒤 진행하며 임의로 Flyway 기록을 지우지 않습니다.
3. MyPage 장보기의 계란 항목에서 `확인한 단위 추가`: 단위 `개`, 수량 `2`, 근거 `레시피 원문/직접 확인` 등을 입력하고 변경 저장합니다. 기존 g가 있으면 그대로 보관됩니다.
4. 가격 비교에서 `개`를 고르고 필요한 개수가 반영됐는지 확인합니다. 계란 10개 5000원 상품이면 1개당500원, 2개 필요 시 1포장 구매5000원·잔량8개로 비교합니다.
5. 같은 상품에 중량도 명시돼 있다면 g로도 비교할 수 있습니다. 저장 후 장보기로 돌아가 예상금액이 한 번만 합산되는지, 구매금액이 별도로 표시되는지 확인합니다.
6. 실제 상품 카드의 버튼/체크박스가 보기 좋게 정렬되는지 확인합니다.

## 검증 결과와 한계
- Python 기존·추가 테스트 58건 통과: g/kg/ml/L·묶음·개수·계란 반복 라벨·난각번호 오인 방지·수집/저장/스케줄 회귀.
- 관련 Node 테스트 54건 통과: 원문 단위 보존·개수만 있는 재료·여러 단위 합산/불완전 단위 보존·장보기 요청의 메타데이터 유지·단위별 조사 예산 선택·실제 상품의 g/개 선택 요청·구매금액/배송비/명시적 저장 회귀.
- Java 다중 단위 계약 검사 19건 통과 및 변경한 모델/서비스/식단 코덱 컴파일 통과. 실제 KAMIS TSV에서 계란2개 예상금액이 계산되는 것을 확인했습니다. Spring/JDBC/Jackson 등의 의존성은 테스트용 시그니처로 격리했으므로 실제 DB 저장/JSON 직렬화 실행을 검증한 것은 아닙니다.
- 기존 Python DB→TSV→실제 Java 가격 조회 하네스도 통과했습니다.
- 전체 Gradle/Spring Boot 기동, MySQL V33 실행/트랜잭션, Jackson 실제 스냅샷 저장·재조회, 실제 로그인·상품 저장, 외부 API 호출 및 버튼 렌더링은 미검증입니다. 사용자 PC에서 기동/저장/재조회가 필요합니다.
- 별도로 실행한 기존 shopping-storage.test.mjs는 변경하지 않은 MyPage 배포 번들의 특정 축약 변수명 문자열 검사에서 실패했습니다. 이번 54건 통과 집계에 포함하지 않았으며 해당 번들 검사를 수정하거나 성공으로 처리하지 않았습니다.
