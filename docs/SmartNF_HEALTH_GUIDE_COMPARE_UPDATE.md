# 건강별 식품 가이드 · 기준 비교 및 건강관리 계획

2026-11-04 / 기존 HEALTH_FOOD_GUIDE_UI_UPDATE 및 PLAN_UX_UPDATE 적용 환경 기준.

## 반영 내용

1. **2. 식품 선택 기준**: 왼쪽 선택 요령, 오른쪽 일반 기준·관리 기준과 출처.
2. **3. 식품 살펴보기**: 왼쪽 목록, 오른쪽 선택 식품 기준량의 영양 비교. 카드 또는 ‘영양 비교 보기’ 클릭은 상세 조회이며, ‘나의 선택에 담기’는 별도다. 모바일에서는 닫을 수 있는 하단 패널을 사용한다.
3. 음식·식재료는 원자료의 100g, 음료 등은 원자료의 100mL 기준을 유지한다. g↔mL 변환이나 1인분 가정은 하지 않는다. 합계·개인 목표 입력·실제 섭취 판정은 제공하지 않는다.
4. 일반 기준은 식약처 영양표시용 공통 기준이며 연령·성별 권장섭취량이 아니다. 열량 2,000kcal는 비교용 참고값이다. 하루 제한 기준과 영양표시 기준치를 구분한다.
5. 나트륨(혈압)·식이섬유(혈중 지질)처럼 검증된 고정 수치는 비교한다. 포화지방의 총열량 비율, 당뇨병의 개별 탄수화물 목표 등은 고정 g으로 임의 환산하지 않고 관리 요령을 표시한다. 정보 없음/미량/미측정은 0으로 계산하지 않는다. 참고 레시피의 전체 영양 그래프는 기준량 미검증으로 표시하지 않는다.
6. ‘음식 예시’ 탭·카드 머리말을 ‘음식’으로 변경했다. 실제 연결 근거에서 공식 식단 예시라는 설명은 유지한다.
7. 가이드의 저장은 **HEALTH(건강관리)**, 영양정보의 저장은 **GENERAL(일반)** 로 구분한다. 장보기/외식 종류와 날짜·메모는 기존 방식을 유지한다.
8. MyPage 기존 달력에 **건강관리** 건수를 추가했다. 장보기/외식 건수는 일반 계획만, 건강관리 건수는 건강관리 계획만 센다. 각 항목을 누르면 해당 날짜·구분을 조회한다. 상세에 혈압/혈당/혈중 지질/체중 관리 목적과 식품·참고 재료·메모를 표시한다.
9. 이름·가족관계·검사값·복약·알레르기는 추가 저장하지 않는다. 관리 목적은 로그인 계정의 계획 분류이며 대상자의 진단 사실을 뜻하지 않는다. 관리 목적을 추가 저장하므로 저장 안내 버전을 갱신했다. 기존 동의를 자동 승계하지 않는다. 기존 계획은 삭제하지 않고 새 안내 확인 후 다시 조회할 수 있다.
10. MyPage 편집·날짜 복사·영양정보에서 추가 저장·식생활 가이드의 식당/시간 수정 경로 모두 계획 구분과 관리 목적을 유지한다. 기존 계정별 접근, CSRF, 수정 버전, 재시도 중복 방지, 동의 철회/탈퇴 삭제는 유지한다.

## 적용

1. 서버를 종료하고 프로젝트 및 DB를 백업한다.
2. ZIP 내부 `src/`, `frontend/`, `docs/`를 **프로젝트 루트**에 병합한다. 상위 포장 폴더는 없다. 기존 migration V1~V12는 변경하지 않는다.
3. `./gradlew.bat test`를 실행한다. 새 `FoodPlanTests.healthScopeCountsPurposeValidationPreservationAndRequestHash`가 포함되어 있다.
4. 서버를 시작한다. Flyway **V13__health_food_plan_scope.sql**이 새 열·새 계획 저장 안내를 추가한다. 운영 DB 마이그레이션 실행은 사용자 환경에서 확인해야 한다.
5. Ctrl+F5 후 건강별 가이드에서 관리 목적→음식 보기→담기→건강관리 계획 저장을 확인한다. 새 저장 안내 동의가 필요할 수 있다.
6. MyPage ‘장보기·외식 계획’ 달력의 **건강관리**를 눌러 상세를 확인한다. 다시 로그인한 후 복원과 수정·삭제를 확인한다.

React 번들 `personal-mypage.js`를 포함하므로 적용만 할 때 npm 빌드는 필요 없다. 향후 React 재빌드는 기존 프로젝트 의존성을 설치한 뒤 `frontend`에서 `npx esbuild src/mypage.jsx --bundle --minify --format=iife --outfile=../src/main/resources/static/js/personal-mypage.js`를 사용한다.

## 검증 결과와 한계

- Node 검사 15개: 영양 단위/결측/수치 기준, 관리 목적 보류 정책, 기존 레시피 연결·선택 회귀 통과.
- React 번들 생성 및 변경 JS 문법 검사 통과.
- Chromium + 실제 정적 파일/JSON + 가상 API 응답: 식품 조회와 담기 분리, 수치 그래프, 질환 기준 전환, 건강관리 저장 payload와 기존 목적 보존, 달력의 건강관리 건수 클릭·상세 필터 통과. 320/390/800/1440px 가로 넘침 없음, JS 오류 없음. **실제 Spring API 저장 검증은 아니다.**
- Java 21에서 실제 모델·카탈로그 컴파일 및 입력 검증 실행 통과. 서비스는 JDBC/annotation 테스트용 타입으로 컴파일 확인했으며 Spring 런타임 검증과 구분한다.
- SQLite에서 새 열의 기존 행 GENERAL 기본값과 실제 집계 SQL의 일반/건강관리 분리·계정 필터 확인. **MySQL/Flyway 통합 검증은 아니다.**
- 프로젝트 전체 Gradle 검사는 Spring Boot 4.1.1 플러그인 해석 실패로 시작하지 못했다. 별도 임시 4.0.2 호환 검증 환경도 저장소 해석에 실패했다. 프로젝트의 Spring Boot/Gradle 버전은 바꾸지 않았다. 따라서 새 JUnit/Spring/H2 테스트는 사용자 환경 실행이 남아 있다.
- 실제 MySQL V13 적용, 재로그인 복원·동의 철회·탈퇴·동시 탭 충돌의 서버 회귀는 사용자 환경 확인 대기다. 암호화·운영 보유기간·백업 삭제 등 105절의 미완료 운영 보안 계획은 이번 변경으로 완료되지 않는다.
