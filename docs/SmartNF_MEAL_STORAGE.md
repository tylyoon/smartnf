# SmartNF 식사·영양 저장 / 가상 회원 5명 추가 적용

## 적용 순서

이미 가상 회원 5명이 생성된 DB를 그대로 사용한다. 기존 가상 회원을 삭제할 필요 없다.

1. 실행 서버를 Ctrl+C로 종료하고 ZIP을 프로젝트 루트에 덮어쓴다.
2. 테스트한다.

```bash
bash ./gradlew test --no-daemon
```

3. 성공 후 기존 5명에게 식사 자료를 추가한다.

```bash
bash run_local.sh demo-seed
```

기존에 정한 공통 개발용 비밀번호를 두 번 입력한다. 이미 생성된 계정의 비밀번호는 바꾸지 않는다. V9 마이그레이션은 기존 Flyway 설정으로 자동 적용된다. 기존 회원은 `created=0, kept=5, deleted=0` 출력이 정상이며, 별도 식사 추가 루틴이 실행된다. 실제 삭제/철회 여부와 날짜별 기존 식사 버전을 확인한 뒤 적합한 가상 계정에만 추가한다. 생성기 출력은 Windows 한글 깨짐을 피하기 위해 ASCII로 바꾸고 Java 컴파일 인코딩은 UTF-8로 명시했다. 모든 JVM/터미널의 한글 출력을 전부 검증한 것은 아니다.

4. `smartnf1@smartnf.com`~`smartnf5@smartnf.com`으로 차례로 로그인하고 `/mypage`에서 Ctrl+F5 후 **식사·영양 기록**을 선택한다.
5. 11월 1일 또는 이전 달의 10월 25~31일을 선택한다. 오늘(11/2)의 식사 목록이 비어 있는 것은 정상이다. 식사 시각·부분 기록은 가상 예시다. 5번은 10/26·28·30을 비워 둔다.
6. **실천·측정 기록**의 날짜 버튼은 윗줄 `2026년`, 아랫줄 `10월 25일`이다. 옆 `식사 기록` 버튼으로 같은 날짜 식사로 이동할 수 있다.

일반 실행은 기존대로 `bash run_local.sh`이며 자동으로 자료를 만들지 않는다. 가상 계정 전체 삭제 명령 `bash run_local.sh demo-delete`는 식사 기록도 삭제한다. 실제 사용자 계정은 대상이 아니다.

## 기존 자료 보존과 동의

- 가상 회원의 기존 건강정보·일일 기록·카드 구성·비밀번호는 유지한다. 전용 `MEALS_V1` 표시가 없는 가상 회원에게만 초기 식사를 추가한다.
- 해당 날짜의 식사 버전이 이미 존재하면(삭제한 날짜 포함) 초기 예시를 넣지 않는다. 이후 재실행은 편집/삭제한 식사 자료를 복원하지 않는다.
- 탈퇴·정지 계정과 최신 건강 동의가 철회된 가상 계정은 자동 재동의/복구하지 않는다. 따라서 철회한 계정에는 의도적으로 초기 식사를 추가하지 않을 수 있다.
- 가상 회원은 내부 개발 표시가 있는 합성 계정에 한해서 갱신된 안내에 합성 동의 이벤트를 기록한다. 실제 사람의 동의를 대신하지 않는다.
- 일반 회원은 저장 안내 버전 `dev-health-20261102-meals`를 직접 확인하고 동의해야 한다. 기존 건강정보를 지우는 마이그레이션은 아니며, 재동의 후 기존 건강정보/일일 기록을 다시 조회할 수 있다. 저장 동의를 철회하면 식사·실천·프로필·관리항목 내용을 모두 삭제한다.

## 입력·저장·수정·삭제

- 날짜 선택 → 끼니/음식/먹은 양(g)/선택 시간/메모 입력 → **저장 전 목록에 추가** → **날짜 기록 저장** 순서다.
- 식사 목록에서 음식 편집/제거 후 날짜 기록 저장을 눌러야 DB에 반영된다. 자동 저장하지 않는다. 다른 메뉴/날짜 이동과 페이지 종료에는 저장 전 변경 경고가 있다.
- 모든 음식을 지우려면 **이 날짜 식사 전체 삭제**를 사용한다. 복구 기능은 없으며 삭제 버전·요청 참조는 충돌 방지를 위해 남고, 저장 동의 철회 때 함께 삭제된다.
- 충돌 시 입력은 유지하고 재저장을 막아 다른 탭의 기록 덮어쓰기를 방지한다. 다시 불러오기 전 필요한 입력을 확인한다. 네트워크 실패 후 동일한 요청은 같은 UUID로 재시도한다.
- 날짜당 음식 최대 50개, 1개당 0 초과~2000g 소수 1자리, 시간은 비워두거나 HH:mm, 음식명 120자·메모 500자다. 본인 회원 ID는 요청에서 받지 않고 인증에서 정한다.

## 성분 자료와 제한

현재 성분 연결은 프로젝트가 이미 보관한 **농촌진흥청 국가표준식품성분표 10.4의 5종 고정 부분집합**이다. 자동 전체 검색·기존 공개 페이지 선택 식품 가져오기는 아직 없다. 그 밖의 음식은 이름·섭취량을 직접 기록할 수 있으며 성분은 정보 없음으로 표시한다.

서버가 식품 ID를 검증하고 이름·성분·출처·버전을 확정한다. 클라이언트가 보낸 임의 영양값은 저장하지 않는다. 저장 항목은 당시의 100g 가식부 성분 스냅샷을 보관하며, 조회 때 현재 카탈로그 값으로 바꿔 계산하지 않는다. 원자료와 실제 제품/조리법은 다를 수 있다. 숫자가 없는 성분과 직접 입력 음식은 0으로 만들지 않으며 성분 확인 개수를 표시한다. 저장된 목록의 영양 합계이며 저장 전 편집·빠진 음식·양념·조리유를 포함하지 않는다. 하루 전체 섭취량/영양 적정성/식사 효과를 판단하는 기능이 아니다.

가상 예시는 5명, 37일, 136개 음식 항목이다. 1~4번은 각각 8일, 5번은 5일이다. 끼니별 일부 식품과 성분 미연결 외식 예시이며 완전한 식단·개인별 권장 식단이 아니다. 공개 체험 화면의 메모리 자료와는 별도이며 개인 계정의 식사 DB에 저장된다.

## 저장 설계

| 테이블 | 역할 | 충돌·권한 기준 |
|---|---|---|
| health_meal_days | 회원별 날짜, 수정 버전, 삭제 표시, 저장 동의 이벤트, 갱신 시각 | 회원+날짜 유일, 회원 행 잠금 후 expectedRevision 검사 |
| health_meal_items | 끼니·음식·g·시간·메모, 원본 성분/출처/버전 | 날짜 행의 자식, 본인 날짜 경유 조회·전체 교체 |
| health_meal_requests | 회원별 UUID, 날짜·작업·결과 버전·요청 해시 | 같은 내용·결과에 한한 재시도, 다른 날짜/내용/오래된 결과 재사용 409 |

인증된 `/api/me/health/meals`에 day/range/catalog GET, 날짜 전체 save/delete POST를 추가했다. 기존 Spring Security·CSRF·세션/계정 상태·no-store 응답을 유지한다. 현재 동의 이벤트가 맞지 않으면 저장을 거부한다. 생성·교체·삭제는 트랜잭션이며 건강 동의 철회/계정 탈퇴 때 식사와 요청 메타데이터도 지운다. 식사와 혈압/체중의 통합 분석·자동 피드백·외부 AI 전송은 미구현이다.
