# 개인 맛 선호를 새 Gemini 레시피에 적용 (197절)

## 적용 데이터와 화면

사용자가 저장·재접속 복원 확인을 완료했다고 보고한 뒤 새 추천 연결을 구현했다. 추천 화면에 내 취향 반영(기본 해제)을 두고 체크했을 때만 GET /api/me/recipes/preferences로 요약을 읽는다.

서버는 기존 RecipeTastePolicy를 사용한다. 회원별 MyRecipe 현재 평가를 읽고 같은 음식명은 한 음식으로 센다. 각 맛 축에 유효한 서로 다른 음식 3개 이상이 있어야 선호 평균을 사용한다. 별점만 있고 실제 강도가 없는 평가는 강도 평균의 재료로 삼지 않는다. 순수 표시를 위해 읽는 프로필과 새 생성 요청에서 적용할 프로필은 모두 서버에서 계산한다.

자료가 부족하면 수동 선택으로 시작한다. 간단한 매운맛·짠맛·기름진 정도를 0/1/3/5로 선택하고 나머지는 제한하지 않는다. 직접 선택은 이번 요청에만 반영하며 DB 프로필 변경/자동 학습은 없다. 저장된 프로필은 최대 6개 맛 축 중 확인된 축만 반영한다.

## 서버 연결

RecipePreferenceService가 회원 경계 안에서 기존 JSON 평가를 읽는다. RecipePreferenceController가 no-store 읽기 API를 제공한다. 기존 CurrentHealthMember를 재사용하며 화면 계정 표식을 요청에 포함한다.

RecipeGenerationController 요청에 usePreferences/manualTasteEnabled/preferredTaste를 추가한다. 값이 없으면 기존과 동일하게 OFF이다. OFF일 때 프로필을 읽거나 맛 조건을 Gemini에 보내지 않는다. 저장된 취향을 사용할 때는 브라우저가 보낸 프로필 숫자를 신뢰하지 않고 서버에서 다시 계산한다. 수동값은 기존 맛 축 allowlist와 0~5 정수 검증을 사용한다. 빈 수동값·저장 프로필 부족은 요청을 거부하고 직접 선택을 안내한다.

원래 추천 입력을 recipeConditions로, 최소 맛 강도 요약을 tasteTargets로 전달한다. 회원 ID·저장 레시피·별점 원문·평가 이력은 이 취향 데이터에 넣지 않는다. 보충 추천에도 동일한 조건이 유지된다. 기존 최대 5개·최대 1회 보충·중복/재료/분량 검증은 유지한다.

프롬프트에서 기존 질환별 식사 기준·열량 상한·제외 재료·보유량을 우선하고, 이를 지키는 범위에서 양념과 조리법을 조절하도록 요청한다. 취향을 맞추기 위해 제외 재료를 추가하거나 양념을 과도하게 늘리지 않도록 지시한다. 이것은 프롬프트의 우선순위이며 개인별 의료 적합성이나 모든 조리 결과를 보장하는 검증기는 아니다. 기존 서버 검증 범위는 유지한다.

X-SmartNF-Taste-Applied에 적용한 조건 요약을 넣어 결과 안내에 표시한다. 조건 적용은 요청 내용에 포함했다는 뜻이다. 생성된 음식의 실제 맛 일치도를 평가하거나 인증한 결과가 아니다. 별도 음식별 추천 이유 생성은 아직 없다.

## 전송 동의·호환

화면에 취향 요약의 Gemini 전달을 명시한다. 체크·기준·수동값 변경 시 기존 Gemini 동의를 해제하고 다시 확인한다. 선택하지 않은 사용자는 기존 흐름 그대로이다. 비밀키·원문·평가를 로그로 출력하지 않는다. 기존 CSRF·보안 설정을 해제하지 않는다. 새 키/모델/DB 마이그레이션은 없다.

기존 재료 찾기·음식명·열량 목표·질환 식사 조건, 사진, MyRecipe 등록, 음식 비교 흐름을 유지한다. 생성 응답 JSON은 기존 레시피 배열 그대로이며 신규 요약은 응답 헤더로 전달한다. 기존 평가/분류 서비스나 저장 프로필을 수정하지 않는다.

## 검사

Java21 + 실제 Spring7.0.1/Security7.0.0/Jackson3.0.2 API로 변경 Java와 기존 TastePolicy를 컴파일했다. 실제 JdbcTemplate/H2에서 회원별 다른 프로필, 부족한 프로필, OFF, 수동 0점 및 범위 검증을 확인했다. 회원 식별만 검사 전용 클래스로 격리했으므로 실제 Spring Security 필터 전체 검사는 아니다.

실제 Java HTTP/JSON 어댑터를 로컬 Gemini 응답 fixture에 연결해 프로필의 최소 전송, 평가 이력 미포함, 동의 없을 때 미호출, 기존 5개 후보, 1회 보충 요청에도 취향 유지, 적용 헤더를 검사했다. 외부 Gemini에 실제 요청한 검사는 아니며 실제 추천 품질 검증이 아니다.

실제 HTML + JS/JSDOM으로 기본 OFF·불필요 프로필 조회 없음, 취향 체크와 동의 초기화, 서버 소유 프로필 요청, 후보 생성 요청/적용 안내, 수동 0점, 부족한 평가의 수동 전환을 확인했다. JS 문법 검사 통과.

전체 Gradle/Spring Boot 빌드와 실제 PC 브라우저 시각 검사·사용자 MySQL/Gemini 추천 품질은 미확인이다. 적용 후 취향 ON/OFF 결과 안내, 직접 선택, 기존 조건 유지와 실제 생성 결과를 사용자 환경에서 확인한다. 이 단계에서 맛 일치나 건강 효과를 보장하지 않는다.
