# SmartNF 식단 화면·공통 사진·자체 LLM 적용 안내

2026-11-09. 기존 SmartNF에 덮어쓰는 변경 파일 묶음이다. 추천·MyRecipe·사진 자동 재검색 및 V18까지 적용한 프로젝트를 기준으로 한다.

## 적용 방법

1. 현재 프로젝트를 Git 커밋 또는 별도 폴더로 백업한다.
2. ZIP의 `src/`, `llm/`, `docs/`를 기존 SmartNF 프로젝트의 같은 위치에 복사한다.
3. 먼저 평소처럼 서버를 실행한다.

```bash
bash run_local.sh
```

4. 브라우저를 강력 새로고침하고 AI 레시피 추천에서 음식명으로 후보를 생성한다. 각 카드의 **영양 비교에 담기**를 체크하고 선택한 음식 비교하기를 누른다. 1개도 확인할 수 있고 2~5개는 함께 비교한다.
5. 불명확한 재료는 DB 항목과 g을 확인한다. 상세 비교에서 식단 구성으로 이동하거나 카드의 한 끼로 구성하기를 누른다.
6. 시뮬레이터에서 한 끼, 주간, 월간을 선택한다. MyRecipe에서 요리를 더 가져올 수 있다. 주간·월간의 이번 초안은 선택한 요리의 순환 배치다. 날짜·끼니마다 교체하고 저장할 수 있다.
7. MyPage 식단 계획 저장 안내에 동의한 계정으로 저장한다. 날짜별로 기존 계획에 추가된다. 저장 후 MyPage의 해당 날짜를 조회한다.

## 자체 LLM 모델 준비

모델 실행기는 llama.cpp를 사용한다. Windows에서는 PowerShell에서 설치할 수 있다.

```powershell
winget install llama.cpp
```

설치가 끝나면 터미널을 다시 연다. SmartNF 프로젝트 루트의 Git Bash에서 모델 다운로드를 진행한다.

```bash
python -m pip install huggingface_hub
python llm/food-parser/download_model.py
```

다운로드 대상은 공개 원 모델 Qwen/Qwen3-4B-Instruct-2507을 GGUF로 변환한 **bartowski의 Q4_K_M 파일**이다. 모델 파일명은 `Qwen_Qwen3-4B-Instruct-2507-Q4_K_M.gguf`, 제공 페이지의 파일 크기는 약 2.5GB다. 다운로드 도구가 저장소 커밋을 고정하고 파일 SHA-256을 확인한 뒤 `llm/food-parser/models/`에 파일과 버전 기록을 남긴다. ZIP에는 가중치가 포함되지 않는다.

실행 PC의 RAM·GPU/VRAM을 아직 확인하지 못했으므로 추론 속도와 적정 실행 설정은 실제 PC에서 확인해야 한다. 다운로드 공간과 실행 메모리는 서로 다르다.

첫 번째 터미널에서 모델 서버를 실행한다.

```bash
bash llm/food-parser/run_model.sh
```

실행된 모델 서버를 그대로 둔다. 두 번째 터미널에서 SmartNF를 실행한다.

```bash
SMARTNF_LOCAL_LLM_ENABLED=true SMARTNF_LLM_PORT=8091 bash run_local.sh
```

이미 SmartNF가 실행 중이라면 기존 서버를 종료한 뒤 위 명령으로 다시 실행한다. Gemini 키는 기존 설정을 사용한다. 모델 포트는 8091이며 SmartNF의 8080과 구분한다. 모델이 준비되면 추천 화면의 **자체 이름 도우미**에서 입력 → 이름 정리하기 → 해석 확인 → 확인한 이름 적용 순서로 사용할 수 있다.

독립 호출 확인도 가능하다.

```bash
python llm/food-parser/normalize.py
```

모델은 사용자가 적은 분량 표현을 보존한다. `조금`이나 `반 모`는 실제 무게 확인이 필요하다. 자체 추가 학습은 독립 평가 자료를 준비한 뒤 진행하는 후속 단계다.

## 사진 공통 연결

헬스케어 식품 상세를 열면 원본 DB ID로 승인 사진을 조회하고, 없으면 자동 검색 대기에 등록한다. 선택과 영양정보 조회는 계속 사용할 수 있다. 완전한 재료명과 조리 상태를 포함해 연결하므로 생것과 조리된 재료가 서로 다른 키를 가진다. 같은 정규 이름의 항목은 같은 사진을 공유한다.

기존 관리자 사진 검토 화면에서 확인·승인한 사진이 표시된다. 자동 검색 간격·검색 제외는 기존 설정을 사용한다. 등록 직후에는 사진이 바로 나오지 않을 수 있으며, 검색·승인 뒤 화면을 다시 열면 확인할 수 있다. 별도의 새 Flyway 마이그레이션은 없다.

## 현재 범위와 후속

| 항목 | 이번 제공 범위 | 후속 |
|---|---|---|
| 음식 비교 | 선택한 1~5개, 1인분 8개 성분, 재료·분량 확인, 막대그래프 | 목표 기준선과 개인화 설명 |
| 한 끼 | 음식 추가·제외·분량 변경, 밥·달걀·채소 조합 후보, 합계·변경 전후 | 개인 조건을 반영한 조합 순위 |
| 주간·월간 | 고른 요리 순환 배치, 날짜·끼니 교체, 기존 MyPage 계획 추가, 첫 7일 재료 합계 | 예산·선호 조건을 적용한 장기 식단 AI 생성·최적화 |
| 전주 비교 | 기존 기록 조회 후 분량 확인, 같은 요일·끼니의 확인 가능한 영양소 비교 | 실제 섭취량을 구조적으로 저장하는 기록 확장 |
| 사진 | 헬스케어 식품 상세에서 공통 조회·검색 등록 | 공통 분류 별칭 관리·목록 썸네일 확대 |
| 자체 LLM | 모델 다운로드·검증 도구, localhost 연결, 이름 해석 확인 화면 | 실모델 평가와 추가 학습 |

주간·월간 저장은 날짜별로 진행한다. 중간 실패 시 저장 확인한 날짜 수를 표시하고 결과가 불확실한 요청은 같은 요청 ID로 확인한다. 모든 날짜가 하나의 DB 트랜잭션으로 저장되는 방식은 아니다. 확인한 끼니의 실제 기록 입력은 기존 MyPage 흐름을 사용한다.

## 확인한 내용

- 실제 공공 영양 TSV를 사용한 Java 계산 로직과 분량·ID 검증을 독립 실행했다. Spring 타입은 검사 환경에서 대체했으므로 전체 Spring Boot 빌드 성공과 구분한다.
- JavaScript 모듈, Python, Bash 구문을 검사했다.
- 브라우저에서는 예시 API 응답을 연결해 음식 1개·5개 비교, 한 끼 합계, 전주 분량 확인, 월간 30일 생성·저장 요청, 390px 모바일 폭을 확인했다.
- 실제 Gemini 재호출, Commons 새 후보 확보, MySQL 저장·재로그인, 실제 Qwen 추론과 추가 학습은 이 환경에서 확인하지 못했다.
